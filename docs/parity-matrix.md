# Parity matrix with IntelliJ IDEA CE 2024.1

Reference: build `IC-241.14494.240`, tag `idea/241.14494.240` of `JetBrains/intellij-community`.

Approved by the user on 2026-10-31 against IntelliJ IDEA CE 2023.2.3 (build `IC-232.10072.27`). Regenerated from 2024.1 on 2026-11-03, as decision 2 of the phase 4 overview says (`docs/reports/phase-4-reference-change.md` lists what changed).

The actions in section 4 come from the source code of that version through `scripts/extract_actions.py`, and their area, phase and status come from the rules of that script. Sections 2 and 3 are written by hand, because they are parts of the interface and settings that are not declared as actions.

The Result column is written by hand and covers phases 1, 2 and 3 as they were checked against 2023.2.3, according to what the code does and what the tests show (2026-11-01 for phases 1 and 2, 2026-11-02 for 3). Each `done` cites its test, or the report of the task that checked it by hand in the real app with throwaway repositories. "Confirm by hand" marks what only a person with a real keyboard or an active window can check. The script does not generate that column: when the table is regenerated it keeps it by action id (`--previous`), and the rows of actions that 2024.1 removed move to the "Removed in 241" list under section 4. New rows have an empty Result until their phase fills it.

In phase 2, `done` means: the Rust logic tested with real git and throwaway repositories or bare remotes, and the interface tested in jsdom with a simulated Tauri API. None of those tests goes through the real IPC or through WebKit with an active window; that is in the manual checklist of `docs/reports/phase-2-validation.md`, and it holds for all the rows, in addition to whatever each one says.

In phase 3, `done` means the same, with real git and throwaway repositories: the Rust logic and the commands, tested with real conflicts, rebases and rewrites, and the interface in jsdom. The merge and interactive rebase windows, and the shortcuts with a physical keyboard, have not been seen in WebKit, and no conflict or rebase has been tried with one of the user's real repositories; that is in the list of `docs/reports/phase-3-validation.md`, and it holds for all the rows of phase 3, in addition to whatever each one says. The classification of the `git4idea.actions.branch.*` rows changed in phase 3 (decision 9).

In phase 4, part 1 (modal commit), `done` means: the Rust logic tested with real git and throwaway repositories, and the interface tested in jsdom with a simulated Tauri API, including the application component (`App.test.ts`) with its stripe, tool windows and diff window. Nobody has seen the `Commit Changes` dialog, the Git tool window or the diff window in a real window (WebKit with an active window), nor pressed ⌘K, ⌥⌘K or ⌘0 on a physical keyboard; that is in the manual checklist of `docs/reports/phase-4-validation.md`, and it holds for all the rows of phase 4, in addition to whatever each one says. The rulings of part 1 that differ from IntelliJ are in the same report.

In phase 4, part 2 (alignment with 2024.1), `done` means the same as in part 1: Rust with real git and throwaway repositories, the interface in jsdom with a simulated Tauri API. Soft wrapping is the weakest case: jsdom lays nothing out, so the wrapping itself, the row alignment of the aligned diff and the jumps when estimated lines are measured were never seen; they are in the manual checklist of `docs/reports/phase-4-validation.md` (part 2, section 5). The rulings of part 2 that depart from IntelliJ are in section 2 of the same report.

In 2024.1 the staging area only exists in the non-modal commit interface, and the user commits in the modal one. The `Git.Stage.*` rows of section 4 say so in the Feature column; their Result is the one of phase 1, which holds for the non-modal interface, and in modal mode they are not shown.

`ActivateVersionControlToolWindow` is not declared in any XML (the platform generates one `Activate…ToolWindow` action per tool window), so `scripts/extract_actions.py` does not produce it; its row in section 4 is written by hand. A regeneration does not drop it: it moves it, with its Result, to the "Removed in 241" list under section 4, and whoever regenerates the table must move it back to section 4.
