# Opening projects: Open… and Recent Projects

How Ramify opens a repository from its own window, compared with IntelliJ IDEA CE 2024.1 (`idea/241.14494.240`). Added on 2026-11-10, after phase 4 part 6, and updated on 2026-11-11 for several project windows (`docs/superpowers/specs/2026-11-10-multi-window-design.md`).

## What it does

- **Open** (the toolbar button) and **File > Open…** show IntelliJ's `Open File or Project` chooser, the native macOS one, for folders only. It starts in the folder typed in the path field, or in the home folder. The chosen folder is opened like a typed one, through the question below. Typing a path and pressing Enter still opens it without the chooser.
- **File > Recent Projects**, below Open…, lists the repositories opened in Ramify, the latest first, as `RecentProjectsGroup` and `RecentProjectListActionProvider` do:
  - Every repository that opens is recorded, from any entry point: Open, a typed path, the path Ramify was started with, a clone opened in a new window.
  - The list keeps 50, the default of `ide.max.recent.projects`; past that the oldest goes.
  - A row shows the folder's name. When two repositories share a name (the window's own one included), each shows its path, from `~` when it is inside the home folder.
  - The window's own repository is not listed. With nothing to list the submenu is disabled.
  - A path that no longer exists stays in the list, as in IntelliJ, in case it is on a drive that is not connected. Choosing it shows `Reopen Project` with IntelliJ's text and `OK` / `Remove From List`.
- **Open project in.** When a repository is already open in the window, opening another asks `Open project in` with `This Window`, `New Window`, `Cancel` and `Don't ask again`, as IntelliJ's `OpenProjectTask` dialog does. The setting `Open project in` (`New window`, `Current window`, `Ask`, default `Ask`) in the Settings view's `System` group holds the answer; `Don't ask again` writes it. With no repository open in the window, it opens there with no question. Opening a repository that is already open in another window focuses that window (the path is resolved to its repository root and canonicalized, so a subfolder, a trailing slash or a symlink match), and nothing opens twice; an open that is still loading counts as open. Opening the repository that is already open in the calling window brings that window to the front and opens nothing again, as IntelliJ's `findAndFocusExistingProjectForPath` matches the calling frame too: its auxiliary windows and its commit message draft stay.
- **Several project windows.** Each project window has its own repository, log, watcher, tasks, console, diff, merge, viewer and selection history windows, askpass and editor prompts. `⌘W` or the red button closes one project window; the others keep working. Closing the last one hides it as before, and the Dock shows it again.
- **Closing a project window** runs the leave flow for that window only (flush its diff window, leave its merge window), saves its commit message draft to the active changelist's comment, cancels its reads and waits up to 60 s for its writes and remote tasks, then destroys its auxiliary windows, drops its session and writes the open list.
- **Quit** (`⌘Q`) runs the leave flow in every window in turn. A refusal in any window stops the quit. The Dock's Quit and logout cannot be stopped; they keep the open list as it was.
- **Reopen projects on startup.** `open-projects.json` in the data folder is a snapshot of the open windows (their repositories in order, and the last focused one). It is written on every open, replacement, close and focus change between windows, and never on quit, so it holds what was open at quit. At a plain start with the setting `Reopen projects on startup` on (the default), the first repository opens in the initial window, the others in new windows, and the last focused one ends focused. A folder that no longer exists is skipped, removed from the list and named in a notification. A start with a path argument opens only that path.
- **Window frames.** Each project window's position, size and maximized or fullscreen state is saved per repository in `window-frames.json` (logical points, 100 projects at most, the least recently saved goes), half a second after the window stops moving or resizing and once more when it closes. When a window opens a repository with a saved frame, the frame is applied if the top of its title bar is still on a connected screen; otherwise macOS places the window as before. A maximized or fullscreen window keeps its last normal bounds.
- **The menu bar** follows the focused project window, or the owner of a focused auxiliary window: the Git menu's enabled state, `Current File`, the GitHub group and Recent Projects. Menu actions go to that window's main window or its viewer; with no Ramify window focused they go to the last focused project window.
- **The project widget**, first in the main toolbar, shows the project's icon (initials on a coloured square) and name, with the path from `~` as tooltip. Its popup lists `Open…` and `Get from Version Control…` (which opens Clone; present in `ProjectWidget.Actions` at the tag), then `Open Projects` (choosing one focuses its window) and `Recent Projects` (the recent list without the open ones; choosing one goes through the question above; a recent folder that no longer exists shows `Reopen Project` with `OK` / `Remove From List`, as in the menu). Esc closes the popup, also with the focus on the widget's button.
- With a modal dialog open, File > Open… and Recent Projects do nothing, like the Git menu.

The list lives in `recent-projects.json` in Ramify's data folder (`~/Library/Application Support/dev.ramify.app`), never in a repository. It is written to a temporary file and renamed, and read again right before each write, so what another Ramify window recorded stays. The submenu is rebuilt when a repository opens and when Ramify gains the focus.

## Differences from IntelliJ

- **Import from IntelliJ.** IntelliJ's own list (`recentProjects.xml`) is not read: Ramify's list starts empty and fills as repositories are opened in Ramify.
- **Manage Projects…** The searchable window IntelliJ puts at the end of the submenu does not exist. The list is only managed by opening repositories and by `Remove From List`.
- **Groups, the Dock menu and the limit.** No project groups, no recent projects in the Dock menu, and the limit of 50 cannot be changed.
- **Recent list and open projects.** IntelliJ never drops a project that is open when trimming to the limit. Ramify trims the stored recent list to 50 without looking at open windows, so the 51st oldest goes even if it is open (it comes back when that window opens it again). The widget's cap of 100 (IntelliJ's `MAX_RECENT_COUNT`) applies to the recent section only, while IntelliJ counts open and recent together; because the stored list keeps 50, the section shows at most 50 rows. Cost: the cap of 100 is reached only if the stored limit is raised.
- **Files.** IntelliJ's chooser also opens single files and project files (`.ipr`); Ramify's opens folders only.
- **Two windows at once.** The file has no lock: two windows recording at the very same moment can lose one of the two entries until that repository is opened again.
- **`open -n` still starts a second process.** There is no single-instance plugin. A second process works but does not know about the first, and the open list and recent list are shared files, so the last writer wins. Cost: one repository can be open in two processes; use the Dock, Finder or a path handed to the running app instead (a path given to the running Ramify arrives as an opened-path event and goes through the question above).
- **No Welcome screen, no Attach, no window tabs.**
- **Importing IntelliJ's recent or open projects** is not done (see Import from IntelliJ above).
- **No feedback while a close waits.** IntelliJ shows `Closing project` progress. In Ramify the window simply stays until its writes finish. Cost: a window with a slow push seems to ignore the red button for a while.
- **A closing window waits for its remote tasks, fetch included, up to 60 s.** A fetch is not cancelled, so that no push or fetch is killed half-way and a push waiting for a password keeps its prompt. Cost: a hung fetch holds that window's close for up to 60 s. A multi-remote fetch caught between two remotes when the close starts is cancelled, and skips the remaining remotes; a cancelled read loses no work.
- **Icon colour.** The project icon's initials follow IntelliJ's `AvatarUtils.initials`; its colour is `ColorPalette.select` of the path's hash (`abs(path.hashCode()) % 9`), not IntelliJ 2024.1's persisted rotating counter (`nextColorIndex`), because Ramify keeps no per-project store. Cost: the same project can have a different colour than in IntelliJ.
- **`Git > Current File` with a diff, merge or selection history window in front** has every entry off, also when that window belongs to the project that just took the menu; IntelliJ fills it from the focused frame's selection. Cost: Current File actions need the main window or the viewer in front.
- **A reloaded `main-<n>` page shows an empty window.** The first repository a second window was asked to open is dropped after its first open, so that a finished open stops counting as in progress. Reloading such a page (only possible in development, with `pnpm tauri dev`) shows an empty window until a project is opened in it.
- **A refused quit does not write the held-back open list**, and a project window hidden as the last window, then left open by a refused close of another, stays hidden until its project is opened again. Cost: rare; the list is rewritten at the next change.

## What was proven with tests

- `src-tauri/src/recent.rs`: order without repeats, the limit of 50, a missing file and folder, a damaged file set aside as `recent-projects.damaged.json`, removal, the window's own repository left out, `~` paths for shared names (also against the open repository, and not for a folder that only shares the home folder's prefix).
- `src-tauri/src/commands.rs`: Open… heads the File menu with no accelerator, and a Recent Projects row carries its path and is not a Git menu action.
- `src-tauri/src/windows.rs` and the session, task, console and prompt tests: window labels and owners, two sessions with two throwaway repositories kept apart, events sent to their own window, a closing window waiting for its writes and remote tasks and starting no new ones while another window's tasks run on, concurrent closes keeping the last window, the open list (order, close removes, quit never writes, missing paths skipped), focus instead of reopening by canonical path, and menu routing by focus.
- `src/project/`: the open flow for each `Open project in` value, the question and `Don't ask again`, the project widget (name, tooltip, sections, focusing an open project, opening a recent one) and the icon's initials and colour.
- `src/App.test.ts`: Open, a cancelled chooser and its starting folder, Enter, File > Open…, a recent project that opens, `Remove From List`, `OK`, and both menus doing nothing behind a modal dialog.

## What could not be checked

The native chooser, the menu bar and the submenu were not seen in a real window, and no real repository was opened: the tests simulate the chooser and the Tauri API, and the menu itself cannot be built without a running app. That is for the user to check in the app.

For several windows, no real multi-window run was made by the agents: real window creation, the Dock, `⌘``, focus and the project widget's popup placement, the menu following focus, native opened-path events, and reopening after a real quit were not seen. The checklist is section 5 of the `Multi-window` part of `docs/reports/phase-4-validation.md`.
